# 首页通用决策形态与饮食模式入口 Plan

## 目标和成功标准

目标：

- 打开应用默认进入通用 Choice Agent 首页，而不是饮食推荐首页。
- 饮食能力作为一个清晰的“模式入口”保留，用户可点击进入当前饮食模式。
- 借鉴 `choice-agent` 的高优先级通用入口体验：开放式问题输入、示例选择、决策流程展示和当前能力状态提示。
- 保持现有饮食聊天、餐食维护、公共餐食、Trace 和评估功能可用。
- 不新增后端能力，不伪装已经存在通用决策聊天。

成功标准：

- 无 hash 打开 `/` 时进入通用首页。
- 顶部品牌回到通用首页。
- 首页主文案表达“通用决策系统”，饮食只是当前可用模式之一。
- 首页提供一个开放式“最近在纠结什么”输入区和示例按钮，用于呈现通用决策入口形态。
- 在当前后端尚未支持通用决策创建的前提下，开放式输入不会伪装成已可完整处理；提交后应引导用户进入当前可用的饮食模式或显示清晰提示。
- 首页有明确入口可进入饮食模式。
- 首页可见展示类似 `Understand -> Clarify -> Compare -> Decide` 的决策流程，弱化饮食推荐第一印象。
- 首页明确提示当前完整可用模式是饮食决策，避免过度承诺。
- `#/diet/chat`、`#/diet/meals/personal`、`#/diet/meals/public`、`#/admin/traces`、`#/admin/evaluations` 原路径继续可用。
- 移动端布局不出现文本重叠或按钮溢出。

## `choice-agent` 高优先级借鉴项

本次纳入当前 Plan 的借鉴项只限前端入口体验，不扩展后端通用决策能力：

- 开放式通用输入：借鉴 `choice-agent` 首页“你最近在纠结什么？”的产品入口，让首页第一眼是通用选择问题，而不是“今天吃什么”。
- 示例问题：提供旅行、职业、学习、消费、饮食等跨领域示例按钮；点击后填入输入框，用来传达通用决策范围。
- 决策流程展示：在首页侧栏或卡片中展示“理解需求、确认条件、寻找候选、比较取舍、解释建议”等步骤，突出系统方法论。
- 当前能力状态提示：借鉴老项目演示/在线模式提示，但在 V2 中表达为“当前完整模式：饮食决策；通用入口建设中”。
- 诚实降级：通用输入提交后不调用不存在的通用 API；第一版可以弹出提示或引导到饮食模式，后续再接入真正通用决策创建。

不纳入本次实施的借鉴项包括状态机强化、revision 防陈旧写入、证据质量摘要、通用工作台和搜索 Provider 边界。这些会记录到独立 TODO 文件。

## 设计方案

采用最小可逆的前端信息架构调整：

- 新增通用首页路由 `"/"`。
- 保留 `"/diet"` 作为饮食模式落地页。
- 无 hash 默认跳转到 `"/"`。
- 未知路由回到 `"/"`。
- 顶部品牌链接改为 `#/`。
- 顶部副标题改为通用定位。
- 顶部导航改为：
  - 首页；
  - 饮食模式；
  - Trace；
  - 评估。
- 饮食子页面不再作为顶部一级导航，但在饮食模式页和饮食聊天页内保留入口。
- 通用首页采用两列布局：左侧开放式输入和示例，右侧决策流程与当前能力状态。
- 通用输入第一版作为入口表达，不创建通用决策记录；提交时给出明确提示，并提供进入饮食模式的下一步。

这样可以把“通用首页”和“饮食模式”分开，同时最大限度复用现有代码和路径。

## 关键流程

### 默认首页

打开 `/`
→ `app.js` 检查无 hash
→ `navigate("/")`
→ `render()`
→ `renderGeneralHome()`
→ 展示通用决策 Hero、开放式输入、示例问题、决策流程和饮食模式入口。

### 通用输入第一版

用户在首页输入一个选择问题
→ 点击“开始决策”
→ 前端判断当前没有通用决策创建 API
→ 展示清晰提示：当前完整可用模式是饮食决策，通用决策入口已预留
→ 提供按钮进入饮食模式。

如果输入内容明显是饮食相关，也可以直接引导到 `#/diet/chat`，但不自动发送用户输入，避免未经确认创建饮食会话。

### 进入饮食模式

点击首页饮食模式卡片或顶部“饮食模式”
→ `#/diet`
→ `renderDietModeHome()`
→ 展示现有饮食能力入口、餐食统计和说明
→ 可继续进入聊天推荐、个人餐食、公共餐食。

### 饮食功能页

用户进入 `#/diet/chat` 等原路径
→ 继续使用现有 `renderChat()`、`renderPersonalMeals()`、`renderPublicMeals()`。

## 兼容性和破坏性变更评估

- 原饮食功能 API 不变。
- 原饮食功能页面路径不变。
- `#/diet` 从原首页变为饮食模式入口页，本质上保留同类内容但语义更明确，不属于破坏性变更。
- 无 hash 默认页从 `#/diet` 变为 `#/`，这是预期的用户体验变更。
- 首页新增的通用输入不会创建后端数据，因此不会引入数据兼容问题。
- 顶部导航减少饮食子页面直达项，可能让重度调试用户少一个快捷入口；饮食模式页会提供这些入口作为补偿。

## 风险和边界情况

- 如果 `#/` 的 hash 解析结果为空字符串，需要确保 `currentRoute()` 正确归一化为 `"/"`。
- 如果顶部导航只按完全路由匹配，高亮饮食子页面时“饮食模式”可能不高亮；需要让 `setActiveNav()` 支持前缀或显式归组。
- 首页如果展示饮食统计，要避免加载失败影响主页面。
- 通用输入提交如果只弹提示，用户可能感觉不可用；需要把“当前完整模式：饮食决策”入口放得足够清楚。
- 示例问题不应让用户误以为旅行、职业、学习、消费已经有完整后端流程。
- 移动端顶部导航收拢后仍可能换行，但现有 CSS 支持 `flex-wrap`。
- 文案需要避免承诺尚未实现的通用决策输入/执行能力。

## 验证方案

自动验证：

- `python -m compileall -q src scripts`
- `python -m pytest`

静态行为检查：

- 读取修改后的 `index.html`、`app.js`、`app.css` 关键片段，确认改动真实落盘。
- 检查无 hash 初始化、未知路由、`#/`、`#/diet`、`#/diet/chat` 分支。
- 检查首页示例按钮能填入输入框，提交通用输入不会调用不存在的 API。

浏览器或 HTTP 验证：

- 启动本地服务后打开 `/`，确认首页展示通用决策形态。
- 点击首页示例问题，确认输入框填充。
- 提交通用输入，确认展示能力提示或饮食模式引导。
- 点击饮食模式入口进入 `#/diet`。
- 点击饮食聊天进入 `#/diet/chat`。
- 检查移动端或窄屏下首页和导航不重叠。

如浏览器控制不可用，至少执行 HTTP 页面可访问和静态代码检查，并明确说明未完成视觉验收。

## 技术折衷

- 本次不实现新的通用决策聊天 API，因为当前后端完整业务能力仍集中在饮食领域。
- 本次不重做整体视觉主题，避免扩大范围；优先解决用户反馈中最明显的信息架构问题。
- 保留饮食内部的 `PERSONAL` / `PUBLIC` sourceMode，避免把“饮食模式入口”和“数据源模式”混为一个概念。
- 首页通用输入先做产品入口和能力预告，不写入数据库；后续由独立 TODO 推进真正通用决策流程。
