# 通用对话与决策面板推广 Plan

## 状态与目标

用户已明确批准“执行”；实施及验证已完成。依据同目录 2026-09-04-general-conversation-panel-research.md。

将饮食已验证的“对话主导＋可编辑当前决策”推广到 Travel、Shopping 和 Generic 兜底，所有领域使用同一页面交互壳。保留饮食餐食/三餐/风险能力及现有工作台可用的比较能力。

成功标准：用户可以从首页自然表达需求，在对话中补充/纠正、通过右侧编辑，并看到真实更新的条件与结果；不需要先学会工作台。未支持的计算和模拟数据明确显示。

## 页面与复用设计

从 app.js 的饮食实现原地提取共用 conversation.js（窗口命名空间与现有脚本风格一致），由 index.html 先加载，共享：对话列表、输入草稿、pending/retry、revision、刷新恢复、历史快照、抽屉与焦点、旧请求隔离。

使用少量明确的领域适配函数提供标题、字段定义、结果卡片及 API 操作，不建设组件框架或插件注册系统。app.js 保留路由/领域组装，旧饮食方法改为薄调用，不能保留一份复制的饮食完整交互实现。

- /diet/chat 沿用 DietApi 和现有会话，不迁移用户数据。
- /decisions/{id} 改为同一对话页面；最新候选、理由、待确认、还需补充在右侧。
- 原权重、证据、候选添加/排除/恢复与比较放入“详细比较”展开区；无信息时不强迫用户填写所有评分。
- 旧通用状态无新快照时显示已有 messages 和最新结果，不伪造历史卡片。
- 桌面约 2:1，移动抽屉，与饮食保持一致；记录按 userId + 资源类型 + ID 隔离。

## 首次场景识别

保留 DomainRegistry 为唯一服务端识别源；新增只读 POST /api/v1/decision-domains/resolve，输入 message 和可选 explicit domain，输出 domain、候选场景、明确/待澄清状态和简短问题。前端删除 isDietPrompt 的业务判定。

- 先使用明确的任务线索（饮食选择、购买物品、旅行安排），不能把“推荐”“周末”“买”单词当决定性证据。
- 有明确场景则直接走对应现有创建入口；饮食仍经 DietApi 创建和 chat，以保留刚完成的写入闭环。
- 多场景或信息不足时返回 generic 和待澄清信息，进入共用对话页收集需求，不静默选择注册表第一个命中。
- 模型已配置时可以辅助歧义判别；输出只能选择注册领域，不能自报高置信就覆盖明确用户选择；失败保留规则判断并澄清。
- 场景在页头可见且可纠正。已有决策后只提出切换建议，不自动清空/迁移领域状态。用户明确选择另一场景时预览将使用的需求并创建新决策，旧链接和历史保留。
- Generic 未明确场景时，后续信息明确可提出“按购物继续”等操作；用户一句明确“按购物继续”与按钮选择等效，避免重复确认。

本轮不做同一决策内跨领域结构迁移，也不因旅行对话中出现“吃什么”就自动跳入饮食。

## 每轮操作意图与理解

ComparisonProfile.intent 从固定 compare 标签升级为结构化 ConversationUpdate：clarify/补充、update_fields、refresh_candidates、exclude/restore、add/update_candidate、compare、suggest_domain_change。复用 StageRunner，不创建第二条流程。

规则负责明确指令、数值/单位和简单候选表达；模型通过既有 ModelProvider 补充语义解析，接收当前字段、最近消息和允许的 schema。模型只输出建议 patch，服务端校验后执行，不能直接写整个 DecisionState。

UI 编辑与对话解析走同一个字段变更函数，来源和优先级沿用饮食：最新明确用户操作 > 旧确认值 > 模型推断；未给出的字段不变，空值清空，保留清空标记。模糊冲突保留原值并追问，未确认推断不能升级硬约束。

通用 create/message/command 使用现有 get_runtime_model，确保浏览器模型设置生效。模型关闭时支持核心规则路径；无法确定的语义用短澄清问题，不声称任意自然语言都能可靠解析。

## 领域字段及生效范围

字段描述包含 key、中文名、类型、单位、可编辑性、来源、确认状态及影响（筛选/偏好/仅上下文）。保存在 domainState.conversationFields，Pydantic 校验；不能再将所有字段塞进 SlotBundle。

| 场景 | 首版字段 | 实际作用 |
| --- | --- | --- |
| 饮食 | 现有七类槽位、排除、数据源 | 沿用当前字段状态/排序/三餐，适配到共用页面。 |
| 购物 | 商品类别、预算上限（元）、用途、优先项（价格/性能/便携/续航等） | 类别约束 Provider；明确预算生成 price <= 上限；优先项映射既有 criterion 权重；用途无可用属性时作为搜索上下文并标注。 |
| 旅行 | 出发地、天数、总预算上限（元）、交通时长上限（小时）、优先项（轻松/人少/自然） | 预算/时长映射既有数值过滤，偏好映射 criteria；出发地/天数进入搜索上下文，fixture 不能证明适配时明确标注。 |
| 通用 | 用户目标、候选、用户描述的优缺点和关注点 | 对话添加/修改候选；生成有依据的比较和后续问题；数值评分为可选高级能力。 |

单位/含义不清先问清楚，例如旅行人均/总预算不能混算。偏好映射首版使用明确固定规则（正常 1x、优先 2x），用户高级权重修改优先，避免让模型隐式制造权重。

字段清空撤销对应派生条件/默认偏好映射；从派生关系定位，不删除用户其他手工约束。更新字段后根据影响重新澄清、重取候选或重排；不能只更新标签。

旅行必需信息为出发地和天数；购物先确认商品类别，用途/预算缺失按对推荐的影响逐步追问。允许用户明确“不限预算”，不循环追问。

Generic 不再默认要求三个 0–100 分。支持“选项 A 是……，B 是……”的结构化提取，含糊候选归属先确认。已提供两项文字描述但缺数值时，展示优势/代价对比与缺失信息；不从主观描述凭空制造分数或宣布最优。有明确用户评分时复用现有排序，并标注来源。

## 状态更新、接口与幂等

复用 DecisionState / messages / revision / EditEvent；新增通用字段 patch schema 和轮次快照。扩展现有 command 类型（update_fields、confirm_fields、update_candidate），保留已有 command。

- create/message 新增可选 requestId；旧客户端兼容，新页面必须使用，连同 commandId 覆盖丢失响应后的重试。
- 创建的幂等键按 userId + requestId 定位：使用服务端固定命名空间生成稳定 decisionId，已存在时校验请求指纹；不靠返回给客户端前的临时内存。无 requestId 的旧请求仍使用随机 ID。
- 同 ID 同请求返回保存回执；不同内容拒绝；并发首次创建由数据库主键约束兜底，冲突后读取归属用户的回执，不重复创建。
- mutation、消息、EditEvent、快照和 revision 一次业务提交，异常先 rollback，再保存失败 Trace，复用 repository 的 commit=False 能力。
- 原有通用 API 可操作 diet 的兼容能力保留；新页面识别 diet 后统一用 DietApi，避免新增混合写入。旧 /decisions/{id} 若 domain=diet，读取 sessionId 后进入饮食适配器，保留原 decisionId。
- GET 返回时不暴露内部回执集合；快照不能递归包含所有历史回执。
- 前端串行发送/编辑，409 拉最新状态并保留草稿，重试沿用 ID；切换用户/新会话后旧回包不得污染当前页面。

不扩大重构饮食事务逻辑；可提取已验证的回执/快照纯函数给两边复用，但饮食专属字段和持久化仍留在饮食模块。

## 结果呈现与能力边界

右侧按统一区域展示目标、已确认条件、待确认理解、候选推荐/对比、来源和待补充。内部 provider assumption 不作为用户理解显示。

- 来源必须区分个人/公共库、模拟数据、用户输入、实际搜索。
- 默认排名信息简化为理由和取舍；原分项评分和证据可展开核对。
- 进入澄清、条件更新失败或无候选后，不能把旧推荐标作最新有效结论。
- fixture 不因用户输入了日期/出发地而成为实时行程或报价；未支持的用途/条件明确标注作用范围。
- 不新增专业职业/学习领域，不保证所有场景都有外部候选；先让 Generic 能可靠对话整理和比较用户提供的选项。

## 风险与兼容性

- 保持旧饮食 URL/API 和通用 API 字段兼容，不新增依赖、数据库表或技术栈；JSON 新字段有历史回退。
- 旅行由“字数足够即推荐”改为必要信息澄清，Generic 由必填评分改为对话比较，属于明确产品行为变化，需要更新针对旧行为的断言并增加实质用例，不能简单删除失败测试。
- 共享前端抽取是主要饮食回归风险；先抽取并跑饮食基线，再接非饮食。
- 首次路由歧义、来源与字段作用是关键设计边界；不要新增全自动跨领域迁移或扩大到任意网页研究。
- 模型输出不可信，未知字段、非法单位、伪造来源/分数必须拒绝或转为待确认；已有权限和错误处理不得弱化。
- 不处理原有主题菜单按钮缺事件等无关问题。

## 验证与成功样例

1. 饮食现有 80 项为参考，实施时重新运行实际基线并保存工作区快照。
2. 场景：“推荐一台电脑”→ shopping；“周末买耳机”不因周末走 travel；“周末从上海出发两天一夜”→ travel；混合“去杭州玩，吃什么”→澄清或保持既有 travel；“帮我选一下”→ generic 澄清。
3. 购物：“买电脑，预算 6000”→预算筛选；“改到 8000”→替换；“更看重续航”→比较作用可验证；清空后下一轮不恢复；商品类别修改后不返回原类别候选。
4. 旅行：补出发地/天数、更新预算/时长、取消限制；fixture 明确展示模拟与不适配条件，不宣称实时。
5. Generic：“A 离家近但薪资低，B 薪资高但通勤长”→整理两个候选与取舍；无需先填分数，无依据时不生成虚假最优结论；右侧编辑与对话一致。
6. 普通创建、消息和编辑的同 ID 重试、异内容拒绝、并发创建、409、跨用户读取/写入、失败回滚、刷新、旧链接、旧回包隔离。
7. 全量 pytest、compileall、受影响 JS 的 node --check、git diff --check；检查最终 diff 与占位符。
8. 浏览器覆盖饮食/旅行/购物/兜底完整对话和面板流程，1440px/390px 双主题、草稿/取消/错误恢复/抽屉焦点。
9. mock 模型验证字段解析及失败回退；外部模型/搜索有凭据才做真实端到端，未运行明确标注，不能把 mock/fixture 算作真实验证。
